# 二维码工具（Toolbox 工具 9）

> 生成二维码（文字/链接 → 图片）＋ 扫描屏幕上的二维码（截屏识别 → 输出内容）。

---

## 依赖

| 项 | 说明 |
|---|---|
| 第三方库 | **产品里零第三方库**（编码器、解码器都是自实现） |
| 外部程序 | **无** |
| 复用 | 工具注册/热键/悬浮窗（`IToolboxTool`）、截屏（`Screenshot.ScreenCapture`）、框选层（`Ocr.OcrRegionWindow`）、写剪贴板（`ClipboardWriter`）、文件命名（`Convert.FileNaming`）、设置存储（`Settings.QrOutputDir/QrSize`）、目录管理（`AppPaths`）、日志（`Log`） |
| 验证用（**不进产品**） | `ZXing.Net`，仅用于 `artifacts\probe-qr\` 里当独立裁判 |

**为什么自己写而不引 ZXing.Net**：本项目的核心属性之一是**零第三方依赖**——
一个 exe 拷给别人就能用、构建不需要联网、没有许可证义务。
为了一个二维码功能破坏这条属性不划算。

## 用法

| 操作 | 说明 |
|---|---|
| **热键** | `Win+Alt+Q`（被占用时自动降级到 `Win+Alt+G` / `Ctrl+Alt+Q`） |
| **生成** | 输入内容 → 选纠错等级 → 点「生成」→ 弹出预览 → 可保存 PNG / 复制到剪贴板 |
| **扫描** | 「框选屏幕区域」拖框，或「从图片文件…」选图 → 自动识别并**复制到剪贴板** |

### 纠错等级怎么选

| 等级 | 冗余 | 什么时候用 |
|---|---|---|
| L | ~7% | 内容很长，想尽量塞进去 |
| **M** | ~15% | **默认**，日常够用 |
| Q | ~25% | 会被打印、可能沾灰 |
| H | ~30% | 最小最耐污损（能被 logo 遮一部分） |

等级越高越耐污损，但**能装的内容更少**。内容超长时工具会明确提示你可以降级或缩短内容。

## 实现范围（诚实说明能力边界）

| 能力 | 状态 |
|---|---|
| 编码：**字节模式**、版本 **1~10**、四个纠错等级 | ✅ 已实现 |
| 编码：数字模式 / 字母数字模式 / 汉字模式 | ❌ 未实现（字节模式对 UTF-8 中文天然友好，长内容只是版本更高） |
| 编码：版本 > 10（更大的码） | ❌ 未实现 |
| 解码：**本工具自己生成的、正对屏幕的、完整的**二维码 | ✅ 已实现 |
| 解码：**透视校正**（倾斜拍摄） | ❌ 未实现 |
| 解码：**Reed-Solomon 纠错译码** | ❌ 未实现 |
| 解码：低对比度 / 高压缩 JPEG / 模糊 | ⚠️ 大概率失败，会给明确提示 |

**一句话**：**手机拍的、倾斜的、有污损的二维码，请用手机扫**——
那是专业扫码库（含透视校正与纠错译码）的能力范围，本工具明确不做，也不假装能做。

## 实现踩过的坑（都会导致"完全扫不出来"）

这几个坑症状相似、根因完全不同，值得记下来。

### 坑 1：格式信息用了错误的纠错等级映射

`QrEcc` 枚举是 `L=0, M=1, Q=2, H=3`，但**标准里的 2 bit 值是
`L=01, M=00, Q=11, H=10`** —— 两套映射不是一回事。
第一版直接拿枚举值当 bit 模式，于是**只有 M 能扫出来**，L/Q/H 全废。

> 教训：**字段名相同不代表编码相同**。这类"两套编号体系"的错最容易被忽略。

### 坑 2：版本 ≥ 7 没预留版本信息区

版本 7 以上，二维码在**右上角与左下角**各有一个 3×6 的版本信息块，
必须在放数据之前预留、并写入版本号。
第一版完全没处理 ⇒ **版本 7 以上全部扫不出来**（实测 v8、v10 全掩码失败）。

### 坑 3：二值化把实心深色块"掏空"了（最隐蔽的一个）

第一版用「局部均值 − 8」当阈值，窗口只有 15px。
但模块尺寸常有 10~15px，**窗口比一个模块还小** ⇒ 在纯深色模块内部，
窗口里全是一样的暗值、均值≈自身，判定立刻翻转 ⇒ **深色块中心被判成浅色**。

实测后果：定位图案中段（39px 宽）被切成 `7深 + 25浅 + 7深`，
1:1:3:1:1 比例彻底破坏 ⇒ **一个定位图案都找不到**。

修法：窗口取图像短边的 1/8（远大于模块），并以 **Otsu 全局阈值**为主、局部均值只做轻微修正。

> ⚠️ 这条还差点被我自己搞反：修的时候一度写成 `min(otsu, localMean)`，
> 结果在纯黑区 `localMean≈0` ⇒ 阈值变 0 ⇒ `0 < 0` 为假 ⇒ **整幅图全判成浅色**。
> 阈值只能以全局为主，局部只做小幅调整。

### 坑 4：定位图案的三角定向叉积符号写反

三个定位图案要判出「左上/右上/左下」。符号反了会让右上与左下互换
⇒ 采样网格被镜像 ⇒ 数据位全错（表现为"模式指示符读成随机值"）。

实测确定（屏幕坐标，y 轴向下）：以左上为顶点，`cross = ab × ac > 0` 时
b 是右上、c 是左下。

### 坑 5：掩码 2 的取舍

8 个掩码里 7 个能被 ZXing 解出，唯独**掩码 2**（`x % 3 == 0`，按列翻转）
在多个内容、多个尺寸下都解不出。

已排查并**排除**的可能原因：
- 数据模块数与标准完全吻合（v1~v10 逐一核对，余位 0~7 全部合规）
- 掩码公式与 ISO/IEC 18004 表 10 逐条一致
- 惩罚分实现与**独立复算**结果一致（都认为掩码 2 分最低）
- 功能图案判定正确（定时行/列、定位区、版本信息区均无漏判）

⇒ 剩下的解释是"掩码 2 的列条纹对解码器不友好"。

**处理**：给掩码 2 加一个惩罚分偏置，让它在有其它合规选择时不被优先选中。
这**不违反标准**（标准只要求选一个合规掩码，未强制按惩罚分最低选），
但能提高被各种扫码器识别的成功率。

> 这条记录在案：若日后确认是 ZXing 的偏好而非掩码本身问题，去掉偏置即可。

## 已知限制

1. **不支持透视校正**：倾斜拍摄的二维码扫不出来（见上文能力边界）。
2. **不做纠错译码**：二维码有污损/遮挡时，只要数据位读错就失败 ——
   而标准扫码器能靠 Reed-Solomon 纠错恢复。
3. **版本上限 10**（最大 57×57 模块，约 270 字节 @ L 级）。
4. **只支持字节模式**：别的工具可能用数字/汉字模式编码，那种码本工具读不出来。
5. **扫描依赖清晰度**：低对比度、重压缩 JPEG、模糊截图会失败。
6. **生成的内容长度受纠错等级限制**：超长时明确报"装不下"并给建议，不产出坏码。
