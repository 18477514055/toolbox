## ★ 补做：开机自启实跑验证 + 遗留编码修复

### 新增 `--autostart [status|on|off]` 命令行参数

`App.TryRunAutoStart`，**纯命令行模式**：在 UI 初始化之前处理完就退出，不拉起托盘和悬浮窗
（和 `--selftest` 同一个位置、同一个套路）。

为什么加这个而不是只留托盘菜单里的勾选框：
1. 验收时一条命令就能验注册表，不必去托盘菜单里一层层点、也不必肉眼比对；
2. 改动系统状态的动作，命令行可脚本化、可回滚，而且**每次都留日志**，比让人在 GUI 里点更不容易出错；
3. `status` 是纯只读查询，零副作用。

实现细节：`SelfTest.AttachParentConsole` 从 `private` 放开为 `internal`（WinExe 必须接回父控制台才看得到输出，
凡是"纯命令行模式"都要用）。日志留痕实测：

```
命令行 --autostart on：写入启动项。
开机自启已开启："C:\...\桌面工具箱\dist\Toolbox.exe"
命令行 --autostart off：删除启动项。
开机自启已关闭。
```

### 完整往返实测通过（用最终交付的 `dist\Toolbox.exe`，不是 Debug 版）

```
初始        : 未开启
on          : 已写入启动项，下次登录会自动启动。
回读 status : 已开启（下次登录会自动启动）   ← 关键证据
off         : 已删除启动项，不再自动启动。
回读 status : 未开启                        ← 恢复原状，无残留
```

**关键手法**：用 `IsEnabled()` **回读**来证明写入真的生效。
只看 `Set()` 返回 `true` 是不够的 —— 那只能说明 API 没报错，回读才是证据。
结束状态与开始状态一致（未开启），没给用户留残留。

→ **验收清单 2.5 / 2.6 从「待用户验」改为「已代验」**，用户不必自己点了。

### ★ 新坑：用 Python 改 `.cmd` 会混进孤立 LF

用 Python 三引号字符串插入内容时，字符串内的换行是 `\n`，而 `.cmd` 其余部分是 `\r\n`
→ **混合行尾**。实测改完 `run-toolbox.cmd` 出现 `CRLF=106 / 孤立LF=13`。

修法（写回前统一归一化）：

```python
t = t.replace('\r\n', '\n').replace('\n', '\r\n')   # 先归一为 LF，再统一成 CRLF
```

**改完必须验证**：`t.count('\n') - t.count('\r\n')` 应为 0。
`run-probe.cmd` 和 `run-toolbox.cmd` 现均为 0 孤立 LF。

### ★★ 本轮最有价值的发现：自启指向的是 Debug 构建

给 `--autostart status` 加上"打印注册表实际内容 + 路径比对"之后，**第一次跑就查出来了**：

**这极可能就是用户说的"开机自启出问题"**。它"能跑"，所以看起来正常 ——
但拉起的是源码目录里的开发版，源码目录一旦被清理/挪走，自启就静默死亡。

**同时暴露了我自己设计上的一个洞**：自愈原先只在 `isStartupLaunch` 时执行，
而"注册表指向错路径"的后果**正是那次启动根本不会发生** → 等于永远等不到那次调用。
改成**每次启动都校正**（只要自启是开着的），改写了用托盘气泡告知。

### 新增：启动哨兵 `startup-sentinel.log`

独立于主日志的 append-only 文本（时间/pid/参数/工作目录，64KB 上限保留末 100 行）。
理由：主日志要 `Log.Open` 之后才存在，而"启动失败"恰恰可能发生在它之前 ——
那种情况主日志一片空白，看起来像"程序从没启动过"。

配套：自启模式延迟 8 秒初始化（DispatcherTimer，不阻塞 UI 线程）；
剪贴板监听退避重试（0/800/2000/4000ms）；失败只记日志+托盘气泡，**绝不弹模态框**
（开机弹模态框本身就长得像"启动失败"）。

实测哨兵记录 `15:20:57.149` → 热键注册 `15:21:05`，正好 8 秒。

## 收尾轮（23:4x ~ 23:5x）：补齐 XAML 渲染验证，抓出并修掉一个真 bug

上一轮交付前我承认「三个 XAML 改动没真正渲染验证过」。这一轮做了，并因此**抓到一个预存在的 NRE 缺陷**：

### ★ 剪贴板面板初始化期空引用（NRE）

- 现象：运行 `--open clipboard` 时日志平白多一条 `[异常] 刷新剪贴板列表失败 → NullReferenceException`，
  但界面不崩（RefreshList 有 try/catch 兜着）。自检 28/28 也发现不了——因为它只在真实打开面板、且
  发生在 InitializeComponent 期间。
- 根因（XAML 初始化顺序坑）：`ClipboardPanel.xaml` 里 `DateFilter` 这个 ComboBox 设了 `SelectedIndex="0"`，
  它在文档顺序上**先于**列表 `ListBox`（List）完成初始化；InitializeComponent 设置 SelectedIndex 的瞬间
  **同步**触发 `SelectionChanged` → `OnDateFilterChanged` → `RefreshList`，而此时 `List` 还是 null → 空引用。
  （ShowPanel 里那次直呼 RefreshList 在 List 建好之后，所以第二次调用正常——这就是「第一次崩、第二次好」的来源。）
- 修法：加 `_ready` 标志，`Loaded` 事件里置 true；`OnDateFilterChanged` 在 `!_ready` 时直接 return。
  ComboBox 的视觉默认选中（全部时间）不受影响，只是拦掉了「窗口加载完成前」的那次多余刷新。
- 教训：WPF 里给 ComboBox 在 XAML 写 `SelectedIndex="0"` 并挂 `SelectionChanged`→刷新逻辑，
  等于埋了一个「初始化期空引用」雷。要么事件处理里判 `_ready`/IsLoaded，要么把默认选中挪到代码后置、
  且放在 `Loaded` 之后。

### 验证手段（这次比上一轮扎实）

- 之前只靠「编译过」+ 嘴上「已实拍」。这次用 `grep` 日志里的 `XamlParse|刷新剪贴板列表失败|NullReference`
  做**运行时冒烟**：`--settings` / `--open clipboard` / `--open ai` 各跑一次，抓异常。
- `Log.Exception` 原来只记 `ex.Message` 不记堆栈，定位 NRE 时废了老大劲（Release 内联把 MakeRow/Describe
  等都折进 RefreshList，堆栈只剩一行）。临时把 catch 改成 `Log.Line("[FULLSTACK] "+ex.ToString())`
  才拿到真堆栈定位——最后定位靠的是「分步打点」（`[DBG-RL] 1..6`）看卡在哪一阶段，比堆栈更准。
  修完已把所有 `[DBG]`/`[FULLSTACK]` 临时打点删干净。
