# OCR 截图识字（Toolbox 工具 6）

> 按热键 → 框选屏幕区域 → 识别文字 → **自动复制到剪贴板** + 弹出可编辑的结果窗口。

---

## 依赖

| 项 | 说明 |
|---|---|
| **OCR 引擎** | **Windows 自带**（`Windows.Media.Ocr`）—— **零第三方库、零联网** |
| 最低系统 | Windows 10 1903+（本机 Win11 26100 实测通过） |
| 中文语言包 | 需要系统装有中文 OCR 语言包；本机已装 `zh-Hans-CN` |
| 其他 | 复用本项目的 `ScreenCapture`（截屏）、`ScreenCoordinateMapper`（DPI 换算）、`ClipboardWriter`（写剪贴板） |

**为什么用自带 OCR**：把工具箱分享给别人时，对方**不用装任何东西**——Win10 1903+ 天生就有这个能力，
而且是**离线**的，截图内容不出本机。

---

## 用法

| 操作 | 说明 |
|---|---|
| **热键** | `Win+Alt+T`（默认；被占用时会自动降级到 `Win+Alt+K` / `Ctrl+Alt+T`） |
| 悬浮窗 / 托盘 | 点「字」图标 |
| 框选 | 拖拽画出要识别的区域；**右键或 Esc 取消** |
| 松手后 | 整块区域送去识别，结果窗口弹出，**并已自动复制到剪贴板** |
| 结果窗口 | 文字**可以直接编辑**（OCR 偶有错字，改完再点「复制」） |

热键可在「设置 → 热键 → OCR 截图识字」里改；**留空 = 不占热键**（改从悬浮窗打开）。

---

## 设计要点

- **选区坐标按显示器真实 DPI 换算**（`ScreenCoordinateMapper`），多屏 / 混合 DPI 都不会偏。
- **悬浮窗会临时躲开**（`OpensBigWindow = true`），免得被截进选区内。
- 识别跑在**后台线程**，不阻塞界面；选区遮罩**先关掉再识别**，不让屏幕一直暗着像卡死。
- 结果**自动复制**，因为多数人就是要"识别完直接粘"。
- 复制走 `ClipboardWriter`（带自污染标记）⇒ **不会污染剪贴板历史**。
- 引擎**启动时就探测一次**并写进日志，出问题时一眼能看出是"没装语言包"还是别的。
- 引擎不可用时**在框选之前**就弹出明确提示，不让你框完一片区域才等到失败。

## 已知限制

### 1. OCR 必然有个别字识别错误（引擎固有，非本工具缺陷）

实测数据（`artifacts\probe-ocr\AccOcr.cs`，同一句话「快捷截图能够识别屏幕上的文字」）：

| 字体 | 字号 | 结果 |
|---|---|---|
| 微软雅黑 | 48px | ❌ 「别」→「另刂」 |
| 微软雅黑 | **64px** | ✅ 完全正确 |
| 微软雅黑 | 80px | ❌ 「别」→「另刂」 |
| 微软雅黑 | 96px | ❌ 「别」→「另刂」 |
| 宋体 | 64px | ✅ 完全正确 |
| 微软雅黑 UI | 64px | ✅ 完全正确 |

**结论：** Windows OCR 对某些字形（如"别"）有固有弱点，与帧大小不成单调关系。
**字形相似的字容易混**，典型还有：`1`↔`I`、半角 `．`↔全角 `.`、`0`↔`O`。
⇒ 所以结果窗口**允许你直接改**，这是最实际的兜底。

### 2. 只按**一种语言**识别

Windows OCR 引擎一次只能用一种语言（没有"自动多语言"）。
本工具**优先选中文**（`zh-Hans-CN`），因为中文用户的屏幕上绝大多数是中文。
若你主要识别英文，且中文引擎把英文认得很差，可在系统里调整默认语言。

### 3. 图片过大时会自动缩小

Windows OCR 上限是 10000 px。超过会自动等比缩到上限内（会在日志里记一行）。
正常屏幕截图远达不到这个尺寸，这条基本不会触发。

### 4. 竖排文字 / 艺术字 / 低对比度背景

识别率会明显下降。OCR 是纯视觉识别，这类排版超出它的能力范围。

### 5. 系统没装中文 OCR 语言包时

工具会**明确告诉你**缺什么、去哪儿装（设置 → 时间和语言 → 语言和区域 →
给中文添加「可选功能 → 光学字符识别」），而不是静默失败。

自检里的 OCR 用例（**程序自己画图 → 走产品真实识别路径 → 按编辑距离算准确率**）：

| 用例 | 判据 |
|---|---|
| OCR 引擎可用 | 引擎能创建，打印可用语言与当前引擎 |
| OCR 端到端：造图 → 识别 → 文字对得上 | 三张图（纯中文 / 较长中文 / 中英混排）**准确率均 ≥ 90%** |
| OCR 空白图给出明确失败 | 空白图必须返回失败 + 中文原因，**不能**静默返回空串当成功 |

> 为什么判据是"准确率 ≥ 90%"而不是"逐字一致"：见上面的已知限制 ①。
> 这条用例真正防的是**整条链路断掉**（那种故障的表现是整段返回空、准确率 0%），
> 而不是"偶有一字认错"。见 `DECISIONS.md` 坑 30。

## 实现踩过的两个坑（都会导致"识别永远返回空"）

这两个都是**真实修掉的 bug**，症状一模一样（识别结果永远是空字符串），
但根因不同，而且**堆栈里才能看出区别**：

1. **输入图必须 `Freeze`** —— WPF 的 `BitmapSource` 有线程亲和性，
   而识别在后台线程跑，不冻结就抛 `InvalidOperationException`。
2. **传进来的图可能持有解码器的 Dispatcher 引用** —— 如果来源是
   `BitmapDecoder.Frames[0]`（`BitmapFrameDecode`），`Freeze()` **冻结不掉那层引用**。
   `BitmapFrame.Create(source)` 会去读 `BitmapDecoder.IsDownloading` 从而炸掉。
   ⇒ 解法是把像素拷进一个**我们完全拥有**的 `WriteableBitmap`（见 `ToOwnedBitmap`）。
3. **PNG 编码不许跨 `await`** —— `PngBitmapEncoder.Save` 读 `BitmapFrame` 是线程亲和的，
   若在 `await` 之后再编码，续体可能落在别的线程上。

完整堆栈与定位过程记在 `DECISIONS.md` 坑 30。
